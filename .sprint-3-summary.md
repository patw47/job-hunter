# Sprint 3 — Notifications Telegram Indeed — Résumé d'implémentation

## Ce qui a été implémenté

- **`telegram_notifier.py`** (modifié) — 6 nouvelles fonctions :
  - `_remote_label(offer)` — normalise le champ `remote`/`job_type` en "Remote"/"On-site"
  - `_is_indeed_complete(offer)` — vérifie que title, company, location, match_rate, skills_found, url sont tous non-vides
  - `_build_indeed_card_text(offer)` — carte Telegram Markdown v1 format spec (sans appel LLM)
  - `send_indeed_card(offer, bot_token, chat_id)` — envoie la carte Indeed avec `parse_mode: "Markdown"` + boutons inline
  - `send_card_from_text(text, offer, bot_token, chat_id)` — envoie une carte pré-construite (retour de /analyze Haiku) avec les mêmes boutons
  - `_build_indeed_card_text` format exact : `🎯 *titre* — company / 📍 location | Remote / 🔗 url / *Match* : X% | Skills : ... / ⚡ Source : Indeed`

- **`notification_sender.py`** (nouveau) — CLI orchestrateur des notifications :
  - `_normalize_rate(rate)` — normalise match_rate en float 0-100 (gère string, fraction 0-1, entier)
  - `_call_analyze(offer, bridge_url)` — appelle POST /analyze, retourne `response["result"]` ou None
  - `send_notifications(new_matches, bot_token, chat_id, bridge_url)` — tri desc par match_rate, ≥80% individuel, 60-79% digest, Indeed complet → direct, sinon /analyze
  - `main()` — lit `{new_matches: [...]}` depuis stdin, sort JSON résultat `{ok, sent_individual, sent_digest, errors}`

- **`workflow-main-pipeline.json`** (modifié) — 2 nœuds ajoutés après "Write: Matches + Pending" :
  - **"Notify: Prepare Payload"** (Code) — récupère `payload_b64` depuis le nœud "Qualify: Merge + Prepare"
  - **"Notify: Send Telegram"** (executeCommand) — pipe vers `notification_sender.py` avec env vars Telegram

- **`tests/test_main_pipeline.py`** (modifié) — 5 nouvelles classes, 24 nouveaux tests (92 total, 100% pass offline) :
  - `TestS3AC1IndeedCompleteNoHaiku` — `_is_indeed_complete` + `_build_indeed_card_text` + routing sans /analyze
  - `TestS3AC2IndeedIncompleteFallback` — company vide → /analyze, LinkedIn → /analyze
  - `TestS3AC3DigestSortedMixed` — tri desc, Indeed 78% avant LinkedIn 75%, offre <60% exclue
  - `TestS3AC4Cap25NotifRespected` — 25 offres envoyées, liste vide sans envoi, mix sources
  - `TestS3AC5InlineKeyboardIndeed` — boutons "Générer CV" et "Ignorer" présents, parse_mode Markdown

## Décisions clés

- **`parse_mode: "Markdown"` (v1)** pour les cartes Indeed — cohérent avec le format spec, URL plain-text sans échappement nécessaire. `send_card_from_text` (Haiku) utilise aussi Markdown car le SKILL.md produit du Markdown.
- **`_call_analyze` retourne `response["result"]`** — /analyze via hunter_server répond `{"ok": true, "skill": "offer-analysis", "result": "<card text>"}` ; on extrait le champ `result`, pas le body brut.
- **Tri effectué dans `send_notifications`** avant de passer à `send_digest` — `send_digest` re-trie aussi en interne (double tri inoffensif, offres déjà dans le bon ordre pour les tests).
- **Fallback `send_match_card`** si `/analyze` retourne None (erreur réseau) — évite de perdre silencieusement une offre ≥80%.
- **Payload_b64 réutilisé** depuis "Qualify: Merge + Prepare" (même base64 que pour pipeline_writer) — évite de passer par la sheet Google pour relire les offres.

## Gotchas et contraintes découvertes

- **`_build_indeed_card_text` n'échappe pas** `*` / `_` dans les champs texte (titres, company) — acceptable en pratique car les titres de postes n'en contiennent quasi jamais. Si nécessaire, passer en MarkdownV2 avec `_escape_md2()`.
- **La commande n8n executeCommand** utilise `VAR="val" python3 script.py` inline dans le pipe — bash applique l'env var à la dernière commande du pipe uniquement, ce qui est le comportement voulu.
- **`HUNTER_BRIDGE_URL`** est l'env var attendue par `notification_sender.py` ; si absent, la valeur est reconstruite depuis `HUNTER_BRIDGE_PORT` (défaut 18798).
- **Sprint suivant** : si un sprint ajoute un suivi `telegram_sent=TRUE` dans la sheet MATCHES, il devra appeler `matches_sheet.update_cell` après chaque envoi réussi dans `send_notifications`. Actuellement ce champ est écrit `"FALSE"` par `_build_matches_row` mais jamais mis à jour après l'envoi.
