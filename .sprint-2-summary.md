# Sprint 2 — LinkedIn Playwright Scraper — Résumé d'implémentation

## Ce qui a été implémenté

### `linkedin_scraper.py` (racine du repo → deploy vers `/opt/apps/job-hunter/`)

Script Python complet de scraping LinkedIn via Playwright :

- **Logique deux passes séquentielles** (identique à Indeed Sprint 0) :
  - Passe 1 : `f_WT=3` (Remote) sur les 12 racines de scan
  - Passe 2 : `f_WT=2%2C3` (Remote+Hybrid) déclenchée uniquement si pass 1 < `HYBRID_THRESHOLD` (10 URLs uniques)
  - Cap global strict : 40 offres toutes passes confondues
- **Gestion de session** : cookies stockés dans `SESSION_DIR/linkedin_session_YYYY-MM-DD.json` (rotation automatique par date) — une session par jour, pas de réutilisation cross-date
- **Anti-détection** : User-Agent réaliste, viewport 1280×800, `--disable-blink-features=AutomationControlled`, masquage de `navigator.webdriver`
- **Détection CAPTCHA** : vérifie l'URL et le contenu contre 7 marqueurs (`captcha`, `authwall`, `challenge`, `security check`, `are you a robot`, `unusual activity`, `verify you're a human`) → arrêt immédiat + `CaptchaError` → exit 1
- **Délais aléatoires** : `random.uniform(3.0, 8.0)` secondes entre chaque requête (vérifié par constantes `DELAY_MIN`/`DELAY_MAX`)
- **Déduplication** : par URL entre les deux passes, `seen_urls: set[str]`
- **Normalisation JSON** : même structure canonique 8 champs que Indeed (`url`, `title`, `company`, `location`, `description` tronqué à 500, `job_type`, `date_posted`, `source: "linkedin"`)
- **Sortie** : JSON array sur stdout, logs sur stderr, exit 0 = succès, exit 1 = CAPTCHA ou erreur
- **Fallback sélecteurs DOM** : 4 sélecteurs de card, 4 de titre, 4 de company, 3 de location (résilience aux changements de LinkedIn)

### `workflow-linkedin-scan.json`

Workflow n8n complet (6 nœuds) :
- **Schedule Trigger** : cron `30 12 * * *` (12h30, après Indeed à 12h00)
- **Execute Command** : lance `linkedin_scraper.py` avec `LINKEDIN_EMAIL`, `LINKEDIN_PASSWORD`, `LINKEDIN_SESSION_DIR` depuis les env vars n8n
- **Parse JSON Output** : parse stdout, détecte exit code ≠ 0, signale `CAPTCHA_DETECTED` vs `SCRAPER_ERROR`
- **IF CAPTCHA** : bifurcation — OK → déduplication → output ; KO → notification Telegram
- **Notify CAPTCHA** : POST Telegram bot avec message d'alerte pour Patricia
- **Deduplicate Offers** : filet de sécurité déduplication par URL (scraper déduplique déjà en interne)

Import VPS :
```bash
n8n import:workflow --input=workflow-linkedin-scan.json
n8n publish:workflow --id=job-hunter-linkedin-001
```

## Décisions clés

### Playwright headless + anti-détection plutôt que non-headless

Le VPS n'a pas de display (`$DISPLAY` vide) donc `headless=False` nécessiterait Xvfb. Choix retenu : headless=True avec masquage des marqueurs d'automation (`--disable-blink-features=AutomationControlled`, suppression de `navigator.webdriver`). Si LinkedIn détecte quand même l'automatisation, le CAPTCHA est attrapé proprement et signalé.

### `f_WT=2%2C3` pour la passe Hybrid

La spec indique `?f_WT=2,3 (remote+hybrid)`. La virgule dans l'URL doit être encodée en `%2C` pour être correctement interprétée par LinkedIn. Le workflow n8n affiche `2,3` dans sa documentation mais le scraper envoie `2%2C3` en HTTP.

### Rotation de session par date

La spec dit "ne pas réutiliser la même session sur plusieurs jours". Implémenté via le nom de fichier `linkedin_session_YYYY-MM-DD.json` : chaque jour, si le fichier du jour n'existe pas, le script refait un login frais. Les anciens fichiers (jours précédents) sont ignorés mais pas supprimés automatiquement — un cron de nettoyage peut être ajouté ultérieurement.

### Sélecteurs DOM multiples

LinkedIn change fréquemment sa structure HTML. 4 fallbacks pour chaque type de sélecteur (card, titre, company, location). Le premier qui retourne du contenu est utilisé. Si aucun ne fonctionne, la page retourne `[]` (pas d'erreur fatale).

### Tests 100% offline

Playwright non installé en CI (Ubuntu GitHub Actions). Les tests mockent `run_scan()` entièrement pour les chemins d'erreur, et testent uniquement les fonctions pures (`normalize_offer`, `detect_captcha`, `load_session`, `save_session`) sans dépendance au navigateur.

## Gotchas et contraintes découvertes

- **`pip install playwright --break-system-packages`** : requis sur Debian/Ubuntu récent pour installer dans un venv système. Le flag `--break-system-packages` est nécessaire uniquement hors venv ; dans le venv thehunter il peut être omis, mais le flag est inoffensif.
- **Sélecteurs LinkedIn instables** : LinkedIn A/B teste activement ses classes CSS. Les sélecteurs actuels (`div.job-search-card`, `a.base-card__full-link`, etc.) sont valables mi-2026 mais peuvent changer. Si le scraper retourne systématiquement 0 offres sans CAPTCHA, vérifier les sélecteurs via DevTools.
- **Session LinkedIn expirée** : les cookies LinkedIn expirent après ~1 an mais le compte peut être forcé à se reconnecter si LinkedIn détecte une anomalie. Dans ce cas, supprimer manuellement les fichiers `sessions/linkedin_session_*.json` et relancer le script avec `LINKEDIN_EMAIL` et `LINKEDIN_PASSWORD`.
- **CAPTCHA Telegram non implémenté dans le scraper** : la spec dit "Détection CAPTCHA déclenche arrêt + log (Telegram pas encore implémenté)". La notification Telegram est dans le workflow n8n (nœud `Notify CAPTCHA`), pas dans le script Python directement.
- **`f_WT` sur LinkedIn** : selon la spec, `f_WT=3` = remote et `f_WT=2,3` = remote+hybrid. À valider contre le comportement réel de LinkedIn (qui utilise `f_WT=2` pour Remote et `f_WT=3` pour Hybrid dans certaines versions de l'interface). Si les résultats ne correspondent pas, inverser les valeurs.
- **Offres LinkedIn sans description** : le scraper ne clique pas sur chaque offre pour en charger le détail (anti-bot). `description` reste vide dans la passe de scraping. Le skill `offer-analysis` devra travailler avec `title` + `company` + `location` uniquement pour les offres LinkedIn.
- **Dépendance Sprint 1** : les offres LinkedIn doivent passer par la déduplication SHA-256 (Sprint 1) avant d'atteindre le skill `offer-analysis`. Le workflow LinkedIn connecte directement à `Scan Output` — le nœud suivant dans le workflow global doit être le pipeline de déduplication Sprint 1.
