# Sprint 0 — Couche 1 : Filtres Disqualifiants — Résumé d'implémentation

## Ce qui a été implémenté

- **`layer1_filter.py`** (racine du repo → deploy vers `/opt/apps/job-hunter/`)
  - Fonction publique `apply_layer1(offer: dict) -> tuple[bool, str]`
  - Retourne `(True, "PASS: ...")`, `(False, "REJECTED: ...")` ou `(False, "IGNORED: ...")`
  - Filtre junior/internship sur le titre (regex `\b(junior|internship|alternance|stage|intern|apprenti)\b`)
  - Cascade de détection work-type : `job_type` → `location` → `title` → `description` → unknown
  - Rejet immédiat des offres on-site (`on-?site`, `présentiel`, `in-office`, `sur-site`)
  - Hybride toléré si `location` contient une ville/région de la liste Valais ou Nouvelle-Aquitaine
  - Hybride ailleurs : rejet sauf `full remote possible` (case-insensitive) dans le corps
  - Remote : pass toujours (quelle que soit la location ou l'absence de ville)
  - Unknown : IGNORED (aucune info work-type détectée)

- **`tests/test_layer1_filter.py`** (58 tests, 100% pass)
  - 7 classes : `TestReturnShape`, `TestJuniorFilter`, `TestOnsiteFilter`, `TestRemoteFilter`,
    `TestHybridFilter`, `TestCascadeDetection`, `TestAcceptanceCriteria`
  - Couvre les 6 critères d'acceptance explicites + cascade complète + edge cases (staging, case, diacritics)

- **`setup.sh`** (mis à jour)
  - Déploie `layer1_filter.py` vers `/opt/apps/job-hunter/layer1_filter.py` (mode 640)
  - Insertion après `linkedin_scraper.py` dans la step [5/7] App files

## Décisions clés

- **Cascade `job_type` avant `location`** : `job_type` est l'attribut structurel de la plateforme le plus
  explicite (valeur catégorisée). La spec mentionne Location en priorité, mais `job_type` est vérifié
  en premier car il représente la classification officielle de la plateforme. Dans la pratique les deux
  sont cohérents ; le premier champ positif l'emporte.

- **`IGNORED` ≠ `REJECTED`** : Les offres sans information work-type retournent `IGNORED` (False + reason)
  plutôt qu'un reject dur. Distinction volontaire pour debugging et analytics en aval.

- **Zone tolérée basée sur `location` uniquement** : la vérification de zone pour les offres hybrides
  n'utilise que le champ `location` (structuré), pas le corps. Évite les faux positifs du type "notre
  bureau à Bordeaux recrute" dans une offre basée à Paris.

- **`job_type` values à confirmer** : les valeurs réelles du MCP Indeed restent "À valider"
  (`indeed_mcp_findings.md`). La détection par regex (`\bremote\b`, `\bhybrid\b`, etc.) est robuste
  à tout format de valeur. Un commentaire in-code rappelle la mise à jour nécessaire.

- **Tests 100% offline** : module purement fonctionnel, aucune dépendance externe, pas de mocking requis.

## Gotchas et contraintes découvertes

- **`\bstage\b` vs "staging"** : le mot boundary `\b` évite de rejeter "Staging Environment Engineer"
  (stage dans une autre langue). Validé par test dédié `test_staging_not_rejected`.
- **Diacritiques** : `mérignac`/`merignac` tous deux dans les constantes. Le regex est case-insensitive
  mais ne normalise pas les diacritiques — les deux formes sont nécessaires.
- **`job_type` en production** : ce champ contient souvent le type d'emploi (FULLTIME, CDI) plutôt
  que le mode de travail. La cascade tombe alors sur `location` pour la détection réelle.
  À mettre à jour dès confirmation des valeurs Indeed MCP.
- **Hybride + location vide** : si `job_type=hybrid` mais `location=""`, `_is_in_tolerated_zone` retourne
  False → la branche "full remote possible" est testée. Si absent aussi → REJECTED (pas IGNORED).
  C'est voulu : une offre hybride sans info de localisation ne peut pas être considérée comme dans
  une zone tolérée.
